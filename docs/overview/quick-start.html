Self-Healing Network — Quick Start

How to start the system, check that it works, and what you can do with it. Details in docs/deployment.md and docs/demo-script.md.

1. Two ways to run it

SIMULATION any Mac / Linux laptopLIVE LAB Linux VM with Docker
Networksimulated in Pythonreal emulated network: Mininet + Open vSwitch + Ryu
Failures / attackssyntheticchange the emulated network / real attack programs in the hosts
Telemetrymodelledmeasured (probe packets, switch counters, real pings)
Ready after~15 s~20 s; failures and attacks after ~2.5 min (it first learns normal traffic)

2. Start it

SIMULATION on the Mac

cd ~/Documents/SelfHealing VIEWER_MODE=simulation python3 -m uvicorn viewer.app:app --host 127.0.0.1 --port 8000

Open http://127.0.0.1:8000. Stop with Ctrl+C.

Use the system python3 (it has numpy, scikit-learn, mininet). "Address already in use" = another copy is running: stop it, or use --port 8001.

LIVE LAB on the VM

  1. Start the Ubuntu VM in VMware.
  2. From the Mac terminal:
ssh vamshi@172.16.120.137 cd ~/SelfHealing docker compose up -d make live-dashboard

Open http://172.16.120.137:8000 on the Mac.
Stop: make live-dashboard-stop

VM IP changed? On the VM run ip -4 addr and use the new address.

4. What you can do — Control tab

Inject a failure

KindWhat happensWhat the system does
Link downa cable is disconnecteddetects in seconds, reroutes traffic, reconnects, verifies
Switch / Router downa switch stopsrestarts it, reroutes if traffic used it
High latencya link becomes slow (default 150 ms)moves traffic to a better path
Packet lossa link drops a share of packets (default 20 %)moves traffic to a better path
Bandwidth limita link becomes narrow (default 5 Mbit/s)balances load or reroutes
  • Physical damage (tick box): software cannot repair it — the system must route around it and escalate to a human. Best demo: Link down · sw-a-sw-b · Physical damage.
  • Warning ramp first (seconds): the problem builds up slowly before it hits, so the AI predictor can warn early (Predictions tab). Try High latency · sw-a-sw-b · warning 60 s.
  • Duration: after it, a "technician" repairs the fault and the system moves traffic back (fail-back).

Launch an attack (from h1–h5)

AttackWhat the attacker doesExpected reaction
Port scantries many ports on a serverport_scan / policy violation → trust drops → quarantine
Brute forcemany wrong-password loginsauth_failures → trust drops
Identity spoofingsends packets with another device's IP and MACdropped at the first switch, fingerprint_mismatch → quarantine
Lateral movementtries services its role may not useblocked by policy, policy_violation
Floodvery high packet rate at the web servervolume / flood anomaly → quarantine

Wait ~40 s after start-up before a flood (the detectors first learn normal traffic volumes).

Stay in control

  • Autonomy L1 = every action waits for you (approve / reject in Decisions & Healing); L2 (default) = reversible actions run automatically; L3 = everything automatic.
  • Run demo plays a ~7-minute script: cable cut, switch failure, predicted latency, flood, spoofing.

6. If something goes wrong

ProblemFix
Mac: "Address already in use"another dashboard runs: Ctrl+C it, or kill $(lsof -t -iTCP:8000 -sTCP:LISTEN)
Live lab page does not openon the VM: docker compose ps (both "healthy"?), then make live-dashboard-logs
"the predictor is still learning…"normal for the first ~2.5 min of the live lab; wait for the countdown
Live tests fail right awaythe dashboard and the tests share one network: make live-dashboard-stop first
VM build error "server misbehaving"the VM's DNS hiccupped; run the same command again
Cannot paste into the VM windowuse ssh vamshi@<vm-ip> from the Mac terminal instead
Safety: the dashboard has no login and its controls change the network. Keep the VM on its private network; do not expose port 8000 to the internet.
