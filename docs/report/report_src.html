ABSTRACT

Enterprise networks still depend on administrators to notice failures and attacks and to repair them by hand. Link and device faults are found only after users are affected, configuration changes are made under pressure, and security is enforced at the perimeter, so a compromised or misbehaving device inside the network is trusted by default. The result is long outages, inconsistent responses and little evidence that a repair actually worked.

This project presents an AI-Powered Zero Trust Self-Healing Enterprise Network: a closed-loop system built on Software-Defined Networking (SDN) that continuously observes the network, analyses it with failure prediction and Zero Trust behaviour analysis, decides on repair or security actions with a fused risk score, acts through the SDN controller and finally verifies that every action really worked, rolling back or escalating to a human when it did not. The system is organised in nine modules: an SDN foundation (Mininet, Open vSwitch and a custom Ryu application), telemetry and monitoring, data management and analytics, AI failure prediction, Zero Trust security, an intelligent decision engine, autonomous self-healing, an operator dashboard with login, and an evaluation and deployment module.

All nine modules have been implemented and evaluated on a simulated network with ten seeded runs per condition, and the complete closed loop has also been deployed on a live emulated network (Mininet, Open vSwitch and Ryu in Docker on a Linux virtual machine). In simulation, automated healing reduced the mean time to repair from 78 s to 24 s and the traffic lost by users during outages from 93 % to 33 %; removing verification made the system report 100 % success while about two repairs per run had in fact failed. On the live network every injected failure was detected in about 2 s, every healing action was verified by real pings, a slowly rising latency was predicted 46 s in advance, and every valid real attack was detected within 4 s without quarantining any innocent device. The work is supported by 545 automated unit tests and 44 integration tests on the live network.

Keywords: Software-Defined Networking, self-healing networks, Zero Trust, failure prediction, OpenFlow, Ryu, Mininet, intent-based networking, closed-loop automation, network security.

CHAPTER 1
INTRODUCTION

Enterprise networks connect the computers, servers and services on which an organisation depends. When a cable is cut, a switch fails or a link becomes congested, users lose access to applications, and every minute of downtime has a direct cost. In most organisations these problems are still handled reactively: monitoring tools raise an alarm, an administrator investigates, and the repair is configured by hand on each device. Diagnosis takes time, fixes are applied under pressure, and there is rarely any systematic evidence that the repair actually restored service [1], [2].

Security is handled in a similarly static way. Traditional networks assume that anything inside the perimeter can be trusted. Once an attacker or a compromised device is inside, it can scan for services, try passwords or flood a server with little resistance. The Zero Trust model replaces this assumption with the principle of “never trust, always verify”: every request is checked against the identity, posture and current behaviour of the device that makes it [3]–[5].

Software-Defined Networking (SDN) makes a different approach possible. In an SDN the switches no longer decide on their own how to forward traffic; a logically central controller programs them through a standard protocol such as OpenFlow [6], [7]. Because the whole network can be observed and reconfigured from one place in software, a program can detect a problem, decide how to respond and install the response across the network in seconds. Tools such as Mininet [8] and Open vSwitch [9] allow realistic SDN networks to be emulated on a single computer, and controllers such as Ryu [10] expose the switches to programs written in Python.

At the same time, machine learning has been applied to network telemetry to detect anomalies and to predict failures before they occur [11]–[13], and research on autonomic computing has described systems that manage themselves through a continuous Monitor–Analyse–Plan–Execute loop [14], [15]. What is still missing in practice is a system that brings these ideas together: one that predicts failures, evaluates trust, decides on an action, carries it out and then proves that it worked, while keeping a human operator in control.

This project builds such a system. The network continuously collects telemetry, scores every link for the risk of failure, maintains a trust score for every device from its observed behaviour, fuses these signals into a single risk value, and selects repair or security actions (restore, reroute, load-balance, quarantine or block). Every action is executed through the SDN controller and then verified against post-conditions measured on the network; actions that do not achieve their effect are retried, rolled back or escalated. An operator dashboard shows the whole loop in real time and lets authorised operators approve actions, change the level of autonomy and inject failures or attacks for testing.

1.1 Problem Statement

Enterprise network operations suffer from four connected problems:

  1. Reactive failure handling. Faults are detected only after they affect users, and repair depends on manual diagnosis and configuration. The mean time to repair is therefore long and varies with the availability and experience of administrators.
  2. No early warning. Many failures are preceded by observable warning signs such as rising latency or packet loss, but conventional threshold alarms fire only once a limit is crossed, when it is already too late to act proactively.
  3. Implicit trust inside the network. Perimeter-based security trusts devices once they are inside. A device that spoofs another device’s address, scans for services, guesses passwords or floods a server is often not stopped until significant damage is done.
  4. Unverified automation. Where automation exists, it usually assumes that a command which returned without error has fixed the problem. A configuration change cannot repair a physically cut cable, yet a naive system reports the repair as successful, hiding the outage from operators.

The problem addressed by this project is therefore to design and build a network that detects and predicts failures and security threats, decides on appropriate actions, executes them automatically within operator-defined limits, and verifies every action on the network itself, so that both availability and trustworthiness improve.

1.2 Objectives of the Project

The objectives of the project, refined during implementation, are:

  1. To build a reproducible enterprise test network using Mininet, Open vSwitch and a custom Ryu controller application, with programmatic control of devices, links and impairments (latency, packet loss, bandwidth limits).
  2. To collect telemetry continuously (link status, latency, loss, throughput, utilisation and drops) and evaluate the health of every link and device.
  3. To store telemetry history, derive features and baselines, and generate labelled datasets for failure prediction.
  4. To predict link failures before they happen and to compare statistical and machine-learning models fairly (objective O1: at least 80 % of failures with warning signs predicted at least 30 s ahead with at most one false alarm per hour).
  5. To implement Zero Trust security: device identities, continuous trust scores, behaviour detectors, default-deny access policy and enforcement of every flow by the switches.
  6. To fuse prediction, trust, threat and fault signals into a single risk score and select safe actions (restore, reroute, load-balance, quarantine, block) with configurable levels of autonomy and operator approval.
  7. To execute actions automatically and to verify every action against measured post-conditions, with retry, rollback, escalation and fail-back.
  8. To provide a secure operator dashboard showing the topology, telemetry, predictions, trust, decisions and healing actions in real time.
  9. To evaluate the system with reproducible experiments and statistics, and to validate the complete loop on a live emulated network.

1.3 Scope of the Project

The project covers the complete closed loop from data collection to verified action for a small enterprise network: one core router, two access switches, five user hosts and two servers, plus a redundant variant with a direct link between the access switches and generated campus topologies of up to 547 devices for scalability tests. It covers link, switch and router failures, performance degradations (latency, loss, bandwidth), and five classes of attack (port scanning, password brute force, identity spoofing, lateral movement and flooding).

The following are outside the scope of the project:

  • Deployment on physical enterprise hardware; the live network is emulated with Mininet and Open vSwitch.
  • Wide-area, wireless or multi-domain networks, and routing protocols such as OSPF or BGP.
  • Deep packet inspection, malware analysis and encrypted-traffic analysis.
  • Multi-user role management for the dashboard (a single operator account is provided).

1.4 Relevance / Significance of the Project

Network outages and security incidents are among the most expensive operational problems an organisation faces, and both are aggravated by slow, manual response. By detecting failures within a few seconds, predicting some of them in advance, and repairing or routing around them automatically, the system reduces downtime directly; in the evaluation the mean time to repair fell from 78 s to 24 s. By checking every flow against identity and behaviour, it stops attacks that a perimeter model would allow.

The most significant aspect of the project, however, is verification. The evaluation shows that a system without verification reports every repair as successful while some repairs achieved nothing. Requiring measured evidence for every action makes automated network management trustworthy enough for operators to rely on. The project also contributes a reusable, open test bed: the same intelligence runs on a simulated network for fast, repeatable experiments and on a live emulated network for realistic validation, which makes it useful for teaching and further research in SDN, network security and autonomic systems.

CHAPTER 2
LITERATURE SURVEY

The literature survey followed a structured approach. The scope was defined around five themes that the project combines: network management and SDN, failure prediction and anomaly detection, Zero Trust security, autonomic and self-healing systems, and intent-based networking. For each theme, foundational papers, standards and the documentation of the tools used were reviewed, and each work was examined for its features, strengths and limitations with respect to building a verified, closed-loop network.

2.1 Review of Existing Systems or Related Work

2.1.1 Reactive Network Management

Conventional network management systems (NMS) poll devices through SNMP, display alarms when thresholds are crossed and leave diagnosis and repair to administrators. Kim and Feamster describe how this device-by-device configuration makes management error-prone and slow, and argue for programmable, centralised control [1].

  • Features: device inventories, polling of counters, threshold alarms, dashboards and logs.
  • Strengths: mature, vendor-supported and well understood by operators.
  • Limitations: reactive by design; no prediction; repairs are manual and unverified; no link between monitoring and security decisions.

2.1.2 Software-Defined Networking and OpenFlow

McKeown et al. introduced OpenFlow, which lets a controller install match–action rules in switch flow tables [6]. Kreutz et al. survey the resulting SDN architecture, separating the data plane, control plane and management applications [7], and RFC 7426 defines the corresponding layers and terminology [16]. Mininet emulates complete SDN networks with real Linux network stacks on one machine [8]; Open vSwitch provides a production-grade software switch [9]; and Ryu provides a Python framework for controller applications with OpenFlow 1.3 support and a REST interface [10].

  • Features: centralised view of the network, programmable forwarding, flow statistics, fast reconfiguration.
  • Strengths: enables software to detect and repair problems network-wide; open-source tools allow realistic emulation.
  • Limitations: the controller provides mechanisms, not intelligence; by itself it neither predicts failures nor evaluates trust nor verifies the effect of changes.

2.1.3 Failure Prediction and Anomaly Detection

Chandola, Banerjee and Kumar classify anomaly detection techniques into statistical, classification-based and nearest-neighbour approaches [11]. Liu, Ting and Zhou propose Isolation Forest, an unsupervised detector that isolates anomalies with random partitions [12]. Lakhina, Crovella and Diot show that changes in the entropy of traffic feature distributions reveal network-wide anomalies such as floods and scans [13]. Supervised ensembles such as random forests [17] and gradient boosting [18] are widely used for classification and are available in scikit-learn [19].

  • Features: learn normal behaviour and flag or predict deviations; entropy measures for traffic concentration.
  • Strengths: can give early warning before a hard failure; unsupervised methods need no labelled failures.
  • Limitations: predictions alone do not repair anything; results depend strongly on how representative the training data is; complex models can overfit and raise false alarms.

2.1.4 Zero Trust Security

Kindervag’s Zero Trust model removes the notion of a trusted internal network [3]. Google’s BeyondCorp applied it at scale by authorising every request on the basis of device and user state rather than network location [4]. NIST SP 800-207 defines a reference Zero Trust Architecture with a policy decision point, a policy enforcement point and continuous evaluation of trust [5].

  • Features: per-request authorisation, device identity and posture, least privilege, continuous monitoring.
  • Strengths: limits lateral movement and contains compromised devices.
  • Limitations: architectures and products focus on access decisions; they are rarely integrated with network failure handling, and trust is often static rather than derived from observed behaviour.

2.1.5 Autonomic and Self-Healing Systems

Kephart and Chess set out the vision of autonomic computing: systems that configure, heal, optimise and protect themselves [14]. IBM’s architectural blueprint describes the MAPE-K loop of monitoring, analysis, planning and execution over shared knowledge [15]. Bidirectional Forwarding Detection (BFD) detects failures of forwarding paths quickly with lightweight probes rather than relying on the state of interfaces [20].

  • Features: continuous closed-loop control; fast detection of path failures.
  • Strengths: reduces dependence on human reaction time.
  • Limitations: loops often assume that executed actions succeed; verification and rollback are left to the implementer, and failures that software cannot repair must be recognised and escalated.

2.1.6 Intent-Based Networking

RFC 9315 defines intent-based networking: operators state what they want and the system determines how to achieve and continuously assure it [21]. Separating a decided intent from its implementation allows the same decision to be executed on different networks and checked against its intended outcome.

  • Features: declarative intents, translation into configuration, assurance of outcomes.
  • Strengths: decouples decision logic from device details; supports verification by design.
  • Limitations: concepts are mostly defined at the level of standards and products; few open implementations combine intents with prediction and trust.

2.3 Gaps Identified

  • No closed loop from prediction to verified action. Prediction research stops at alerts; SDN applications act but rarely predict; neither verifies outcomes.
  • Security and reliability are handled separately. Failure management and Zero Trust use different tools and signals, so a single decision cannot weigh a degrading link against a misbehaving device.
  • Automation is trusted blindly. Executed commands are assumed to work; failures that software cannot fix (a cut cable) are reported as repaired.
  • Static trust. Trust is often granted once at authentication instead of being updated continuously from observed behaviour.
  • Few open, reproducible test beds. Results are hard to reproduce without a shared environment that supports both fast simulation and realistic emulation.

2.4 Proposed System

The proposed system closes these gaps with a single closed loop that runs every collection step (2–5 s):

  1. Observe: telemetry from the network — on the live network from active link probes, OpenFlow counters and port status — is collected and every link and device is rated healthy, degraded or down.
  2. Analyse: a predictor scores every link for impending failure; the Zero Trust engine updates each device’s trust score from its real flows and logins and computes a network threat index.
  3. Decide: the decision engine fuses these signals into a risk score and creates intents (RESTORE, REROUTE, LOAD_BALANCE, QUARANTINE, BLOCK, MONITOR) after safety checks and, depending on the autonomy level, operator approval.
  4. Act: the healing engine executes each intent through the network controller and the Ryu REST API.
  5. Verify: each action is checked against its post-conditions measured on the network; failed actions are retried, rolled back or escalated, and successful reroutes fail back after the original fault is repaired.

The same intelligence runs on two interchangeable back-ends: a simulated data plane for fast, reproducible experiments and a live emulated network for realistic validation. A web dashboard with operator login presents the whole loop.

3.1 System Architecture

The architecture is organised into five layers, shown in Fig. 3.1. The presentation layer contains the login page and the dashboard. The intelligence layer contains the four engines that analyse and act: failure prediction, Zero Trust, decision and self-healing. The data and analytics layer collects telemetry and stores its history. The data plane consists of Mininet hosts and Open vSwitch switches on the live network, or of the simulated data plane in simulation mode.

Closed loop. Fig. 3.2 shows the control loop that connects the layers. It follows the MAPE-K pattern [15] but adds an explicit verification stage: an action counts as successful only when its post-conditions are observed on the network.

{{FIG:figs/fig3_2_closed_loop.svg:46:Fig. 3.2: Closed-Loop Workflow (Observe, Analyse, Decide, Act, Verify)}}

Mathematical model. (Equations are numbered as in the project’s research model, which also defines Eq. 1, the calibrated failure probability, and Eq. 5, the path-selection objective.) The trust of a device s at time t decreases with recent anomalies and recovers as they age, with a half-life of 300 s:

T(s,t) = Tbase(s) − Σj wj · aj(s,t) · κ(t − tj)(2)

where Tbase is the base trust from role and posture, aj an anomaly of type j with severity weight wj, and κ the decay factor. The network threat index combines the drop in traffic entropy, the rate of failed logins and the share of anomalous devices:

Thr(t) = mean( Hflow(t), Rauth(t), Fanom(t) ) ∈ [0, 1](3)

The decision engine fuses the failure probability p̂, trust, threat and the known fault indicator into one risk score per target, with policy weights α = 0.30, β = 0.15, γ = 0.15, δ = 0.40 and an action threshold of 0.15:

R(n,t) = α·p̂(n,t) + β·(1 − T(n,t)) + γ·Thr(n,t) + δ·Ifault(n,t)(4)

Alternative paths are chosen with Dijkstra’s algorithm [22] over the edge cost

c(l) = wloss·loss(l) + wlat·latency(l) + wrel·p̂(l) + ε(6)

where the small term ε prefers shorter paths when costs are otherwise equal.

Deployment. On the live lab (Fig. 3.3) two Docker containers run on a Linux virtual machine. The mininet-net container hosts the dashboard, the live runtime, the Mininet hosts with their services, users and attack programs, and the Open vSwitch bridges. The ryu-controller container runs the self-healing Ryu application, which listens for OpenFlow connections on port 6653 and offers its REST API on port 8080.

3.2 Modules Description

The system is divided into nine modules (Fig. 3.4). Each module has a clear input, output and responsibility, and the modules communicate through a shared event bus and well-defined interfaces, so that simulated and live implementations of the same interface can be exchanged without changing the rest of the system.

{{FIG:figs/fig3_4_modules.svg:80:Fig. 3.4: Module Architecture and Dependencies}}

M1 – SDN Foundation

  • Responsibilities: build the topology from YAML configuration; start and stop the network; enable and disable devices; connect and disconnect links; apply latency, loss and bandwidth limits with Linux traffic control (tc netem/htb) [23]; inject and recover failures through a FailureManager with reusable scenarios.
  • Ryu application: loop-safe shortest-path routing between subnets with virtual gateways, proxy ARP (no flooding between switches), pinned paths, drop rules, active link probing and per-flow Zero Trust enforcement, all exposed through a REST API.

M2 – Telemetry and Monitoring

  • Responsibilities: collect link status, latency, loss, capacity, byte/packet/drop counters and node status every step; derive throughput, utilisation and drop rates from counter deltas; rate every element HEALTHY, DEGRADED or DOWN.
  • Live source: one-way latency and loss from probe packets sent five times per second across every link, corrected by half of the OpenFlow echo round trip; a link that loses all probes is down even if its carrier is up, following BFD [20].

M3 – Data Management and Analytics

  • Responsibilities: store telemetry and events in SQLite; resample and clean series; compute rolling-window features (mean, standard deviation, minimum, maximum, last value, change and slope) and behaviour baselines; generate labelled datasets with a prediction horizon and cooldown that prevent label leakage; summarise availability and MTTR.

M4 – AI Failure Prediction

  • Responsibilities: score each link for the probability of failure within the horizon. Six models are compared on separate training, validation and test runs: health thresholds, a z-score baseline, Isolation Forest [12], logistic regression, random forest [17] and gradient boosting [18]. A model registry keeps a champion and challengers; the alarm threshold is chosen on validation data. On the live network the z-score model learns the network’s own normal behaviour during a warm-up period.

M5 – Zero Trust Security

  • Responsibilities: keep device identities (role, owner, MAC, posture); update trust with Eq. 2; run six behaviour detectors (fingerprint mismatch, failed logins, port scan, policy violation, volume anomaly, entropy-based flood); compute the threat index (Eq. 3); decide every request with a default-deny policy; quarantine devices whose trust falls below 0.3, with hysteresis before release.
  • Enforcement: rules are pushed to the Ryu application, which decides the first packet of every new flow at its ingress switch (identity binding, role access, quarantine) and installs a per-flow allow or drop rule; replies to allowed connections are recognised statefully.

M6 – Intelligent Decision Engine

  • Responsibilities: compute the fused risk (Eq. 4); create intents with explicit post-conditions; plan reroutes with Dijkstra and Eq. 6 and load balancing by minimising the maximum link utilisation; apply safety checks (conflicts, cooldowns, blast radius) and the autonomy level (L1 approve all, L2 reversible actions automatic, L3 fully automatic).

M7 – Autonomous Self-Healing

  • Responsibilities: execute intents (restore, reroute, load balance, quarantine, block); verify post-conditions from telemetry, measured traffic delivery and enforcement probes; retry, roll back or escalate; fail back to the original routes once a fault is repaired. On the live network, reroutes are pinned paths and quarantines are drop rules installed through the Ryu REST API, and delivery is measured with real pings.

M8 – Dashboard

  • Responsibilities: operator login; live topology map with health, reroute, prediction and quarantine overlays; telemetry charts; predictions; trust and security events; decisions with approve/reject; healing actions with their verification evidence; timeline and analytics; controls to inject failures and attacks and to change autonomy.

M9 – Evaluation and Deployment

  • Responsibilities: reproducible experiments with fixed seeds and recorded provenance; ten runs per condition with 95 % confidence intervals, paired Wilcoxon tests [24] and Holm correction [25]; baselines, ablations, sensitivity and scalability studies; continuous integration; deployment guide and live-lab experiment.

4.4 Limitations

  • The live network is emulated with Mininet and Open vSwitch on one virtual machine; results on physical hardware may differ.
  • Failures, warning patterns and attacks used for training and evaluation were designed by the project team, so the prediction and detection results show that the designed patterns are learnable, not that real networks exhibit them.
  • The live evaluation is a single round without confidence intervals; the statistical evaluation was performed in simulation.
  • Decision correctness is measured against rules written with the same design as the decision strategies.
  • In the main topology only one link has an alternative path, which limits what rerouting can demonstrate; the scalability study used generated topologies in simulation only.
  • The dashboard uses a single operator account over plain HTTP; it is suitable for a private lab network only.
  • A single volume anomaly does not quarantine a high-trust device; whether floods from trusted devices should be quarantined is a policy decision.

4.5 Conclusion and Future Enhancements

The project designed, implemented and evaluated an AI-powered Zero Trust self-healing enterprise network. A closed loop of observation, analysis, decision, action and verification runs end to end on both a simulated and a live emulated SDN network. Automated healing reduced the mean time to repair from 78 s to 24 s and user-visible loss from 93 % to 33 % in simulation; on the live network failures were detected in about 2 s and every action was verified with real traffic. Zero Trust enforced per flow in the switches detected every valid real attack without quarantining innocent devices. The strongest finding is that verification is essential: without it the system claims complete success while repairs silently fail. Simple predictors matched or outperformed complex models on these data, and prediction adds most value where detection is slow.

Future enhancements include:

  • Repeating the live experiments over multiple rounds to report confidence intervals, and validating on physical switches.
  • Running larger generated campus topologies on the live network and making Zero Trust rule compilation incremental.
  • Training prediction models on recorded real traffic and adding sequence models.
  • Route-aware load measurement and congestion-aware path costs.
  • Multiple operator accounts with roles, HTTPS and audit logging for the dashboard.
  • Integration with standard telemetry (gNMI, sFlow) and routing protocols for production networks.
